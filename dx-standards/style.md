# Developer Documentation Style Guide

## Voice

- direct
- precise
- technically specific
- calm
- active voice where practical
- no marketing claims in technical reference

## Terminology

Maintain one canonical term per concept. If aliases exist, identify the canonical term and use the others only for searchability or migration.

Create a glossary when the domain contains unavoidable specialized vocabulary.

## Instructions

- Start steps with actions.
- State where commands run when ambiguous.
- Separate command from expected output.
- Make destructive steps explicit.
- State prerequisites before the user discovers them through errors.

## Code

- Match current supported versions.
- Prefer realistic variables and resource names.
- Use syntax highlighting.
- Keep snippets focused.
- Include complete runnable versions when onboarding.

## Headings

Use descriptive, task- or topic-specific headings. Stable descriptive headings improve scanning, linking, search, and agent retrieval.

## Warnings

Use warnings for real risk, not for normal explanatory detail. Distinguish destructive/data-loss/security risks from ordinary notes.

## Accessibility

- do not encode meaning by color alone
- provide text equivalents for important diagrams/images
- use meaningful link text
- avoid screenshots for information better represented as text
- use tables only when relationships are genuinely tabular

## International developer audience

Avoid idioms, culture-specific metaphors, ambiguous date formats, and unexplained region assumptions. State timezone, locale, units, and region behavior where relevant.
