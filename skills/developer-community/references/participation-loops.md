# Participation Loops Design

## Loops beyond code

Code is one loop. A community needs at least these six:

- **Triage loop** — issues triaged, labeled, and answered against `COMMUNITY_ISSUE_RESPONSE_P50_H`; stale labeled issues removed (`STALE_GOOD_FIRST_ISSUES`).
- **Support loop** — questions answered from the SUPPORT channels; a useful answer within `COMMUNITY_USEFUL_ANSWER_P90_H` is the design target.
- **Docs loop** — docs issues and PRs owned; docs work is contribution work and appears in recognition.
- **Testing loop** — reproduction confirmation, release-candidate testing, fixture maintenance. Testers are contributors.
- **Design loop** — issue templates that solicit design feedback; design contributors on the ladder.
- **Events loop** — meetups, hackathons, and office hours as issues with owners; event contributors recognized like code contributors.

## Keeping loops alive

Every loop needs:

- a named owner
- a channel where the loop visibly happens
- a cadence — even a slow one
- a failure signal — what happens when the loop goes silent
- a deputy or rotation, so no loop has a single point of failure

A loop with no failure signal is a zombie loop: it runs until it silently dies. Assign each loop a deputy at design time, not when the owner leaves.

## Non-code contribution paths

Design the ladder so non-code labor reaches the same rungs as code: triage, docs, testing, design, and support all count. Publish what counts and how it is measured.

Verify:

- non-code contributors can be promoted, not just thanked
- recognition records non-code work with the same visibility as commits
- no loop is a dead end for its contributors

A community that recognizes only code has a recognition gap even when code contributors are recognized well: `NO_RECOGNITION_PATH`.
