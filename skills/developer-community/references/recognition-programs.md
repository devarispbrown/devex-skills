# Recognition Program Design

## What recognition is for

Recognition is the "return" step of the funnel: it decides whether a contributor comes back. Design recognition for the first merge, not the second-year anniversary. Recognition that arrives late is a thank-you for someone who has already left.

## Credit non-code labor

Triage, docs, testing, design, and support contributions are contributions. Recognition records them, and the ladder credits them toward promotion.

Never let recognition default to commit count. A commit-count leaderboard ignores the triager who keeps the backlog usable.

## First-PR recognition

At first merge, deliver all three:

- a personal acknowledgement from a maintainer
- a welcome message from a person, not a bot
- public credit — the contributors list, release notes, or a label

Do not batch first-PR recognition into a quarterly digest. First merge is the highest-retention moment in the funnel.

## Reviewer promotion

Reviewers are recruited, never discovered by accident. Publish the reviewer path, state the criteria, and promote reviewers with the same ceremony as maintainers.

Verify the reviewer path is a ladder rung with requirements and privileges, not a favor from a maintainer.

## Release acknowledgements

Every release credits all contributors — code and non-code — in the release notes.

Automate the contributor list from git history and issue data. Never automate the message: a person writes the appreciation, a bot assembles the logistics.

## Automate logistics, never appreciation

Automate: contributor lists, labels, tokens, badges, reminders, dashboards.

Never automate: the thank-you.

A bot-generated "thank you for your contribution" is noise that devalues real recognition. If the appreciation cannot be written by a person, the program is logistics without recognition.
